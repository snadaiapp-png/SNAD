## 2. Incident Runbooks

### 2.1 INC-01: AI Gateway Unavailable

**Symptoms:**
- Score calculation returns fallback values
- `AiScoreOrchestrator` logs `error` level: "AI Gateway request failed"
- Audit trail shows `AI_REQUEST_FAILED` events

**Diagnosis:**
```bash
# Check AI Gateway health
curl -s https://ai-gateway.internal/health

# Check recent AI request failures
grep "AI_REQUEST_FAILED" /var/log/application.log | tail -20

# Check AI Gateway connectivity
telnet ai-gateway.internal 443
```

**Resolution:**
1. If AI Gateway is down: Wait for AI Gateway team to restore service. Fallback scores are served from cache/rule-based calculation.
2. If connectivity issue: Check network configuration, security groups, DNS.
3. If timeout issue: Check AI Gateway response times, increase timeout in `CustomerIntelligenceProperties`.

**Recovery:**
- Scores automatically recalculate on next request after AI Gateway恢复
- No data loss — fallback scores are valid

**Prevention:**
- Monitor AI Gateway success rate (SLI-AVAIL-03)
- Alert when success rate <95% (ALERT-WARN-02)

### 2.2 INC-02: Score Calculation Failures

**Symptoms:**
- `CustomerScoringService` throws exceptions
- Score values not updating
- `crm_customer_score_history` not receiving new entries

**Diagnosis:**
```bash
# Check score calculation errors
grep "CustomerScoringService" /var/log/application.log | grep -i error | tail -20

# Check database connectivity
psql -h db-host -U app-user -d sanad -c "SELECT 1"

# Check scoring model configuration
psql -h db-host -U app-user -d sanad -c "SELECT * FROM crm_scoring_models WHERE active = TRUE"
```

**Resolution:**
1. If database issue: Check connection pool, run `SELECT 1` to verify connectivity.
2. If scoring model issue: Verify `crm_scoring_models` has active entries for the tenant.
3. If AI fallback issue: Check `AiScoreOrchestrator` logs for AI Gateway failures.

**Recovery:**
- Trigger manual score refresh: `POST /api/v2/crm/accounts/{id}/scores/refresh`
- Scores recalculate on next customer access (read-through cache)

### 2.3 INC-03: Event Publication Failures

**Symptoms:**
- `SpringCustomerIntelligenceEventPublisher` logs `error` level
- Timeline aggregation not receiving events
- Audit trail incomplete

**Diagnosis:**
```bash
# Check event publisher errors
grep "Failed to publish event" /var/log/application.log | tail -20

# Check Spring application event bus
grep "ApplicationEventPublisher" /var/log/application.log | tail -10

# Check event consumer health
grep "timeline" /var/log/application.log | grep -i error | tail -10
```

**Resolution:**
1. If ApplicationEventPublisher failure: Check Spring context, verify bean wiring.
2. If consumer failure: Check consumer logs, verify consumer is registered.
3. If transaction issue: Verify event is published within transaction boundary.

**Recovery:**
- Events are published within transaction — if transaction rolls back, events are not published
- No retry mechanism — events must be regenerated by re-triggering the operation
- For missed events: Re-trigger the score calculation or segment change

### 2.4 INC-04: Cache Degradation

**Symptoms:**
- Low cache hit ratio (<80%)
- High eviction rate
- Increased database load

**Diagnosis:**
```bash
# Check cache stats
grep "cache" /var/log/application.log | grep -i stats | tail -10

# Check memory usage
jcmd <pid> GC.heap_info

# Check Caffeine cache metrics
curl http://localhost:8080/actuator/metrics/cache.scores.hit
```

**Resolution:**
1. If memory pressure: Increase JVM heap or reduce cache max size.
2. If TTL too short: Increase TTL in `CustomerIntelligenceProperties`.
3. If key collision: Verify tenant-scoped key format.

**Recovery:**
- Cache self-heals on next requests (read-through population)
- No data loss — cache is derived from database

---

### 2.5 INC-05: Database Migration Failure

**Symptoms:**
- Flyway migration fails on startup
- Application fails to start
- Error: "Migration failed"

**Diagnosis:**
```bash
# Check Flyway status
flyway info -url=jdbc:postgresql://db-host:5432/sanad -user=app-user

# Check migration history
psql -h db-host -U app-user -d sanad -c "SELECT * FROM flyway_schema_history ORDER BY installed_rank DESC LIMIT 10"

# Check for failed migrations
psql -h db-host -U app-user -d sanad -c "SELECT * FROM flyway_schema_history WHERE success = FALSE"
```

**Resolution:**
1. If partial migration: Execute rollback script (see `CRM-010-MIGRATION-RECOVERY-DESIGN.md`).
2. If conflict: Check for manual schema changes, reconcile with Flyway history.
3. If data issue: Restore from backup, re-run migrations.

**Recovery:**
- Rollback script available in `CRM-010-MIGRATION-RECOVERY-DESIGN.md`
- Re-run migrations after rollback
- Verify acceptance criteria (6 tables, 6 indexes, 5 capabilities)

## 3. Recovery Procedures

### 3.1 Data Recovery

| Scenario | Recovery Method | RTO | RPO |
|----------|----------------|-----|-----|
| Score data corruption | Re-calculate from source data | <5 min | 0 (scores are derived) |
| Segment data corruption | Re-create segments from definition | <10 min | 0 (segments are configuration) |
| NBA data corruption | Re-generate recommendations | <15 min | 0 (NBAs are generated) |
| Full database loss | Restore from PITR backup | <1 hour | <5 min (PITR interval) |

### 3.2 Service Recovery

| Scenario | Recovery Method | RTO |
|----------|----------------|-----|
| Application crash | Restart application | <2 min |
| AI Gateway down | Fallback to rule-based scoring | Immediate |
| Database connection pool exhaustion | Restart application (pool resets) | <2 min |
| Cache stampede | Wait for TTL expiry, self-heals | <5 min |
